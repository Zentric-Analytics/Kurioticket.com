## Confirmed defects and evidence limits

| Finding | Origin and correction |
| --- | --- |
| The customer page observer could lose an event on a transient network or API failure. | The pre-Phase-1 observer used a single fire-and-forget page request. In Chromium on the immutable `72bc7ffe` baseline, an injected HTTP 503 on the move from Homepage to Hotels produced no automatic retry and no row. Explicit concurrent replay produced one row. The replacement reads the receipt, retries bounded transient failures with the same occurrence, and cancels delivery when consent or actor context changes. |
| HTTP acceptance alone could not establish the result of page capture. | The Phase 1 handler used a JSON receipt for accepted, rejected and pending-link cases. A synthetic authenticated browser verified a homepage visit through consent confirmation, identity merge and persistence on the deployed baseline. This confirms an eligible path existed. The handoff window and previous aggregate counts cannot determine the original tester's outcomes or ownership. |
| Page keys could suppress distinct navigations that reused a detail template. | The original web and native observers deduplicated the sanitized key. The adapters distinguish committed navigation instances locally and send the same safe keys to the server. Route instance identifiers and raw navigation values stay on the device. |
| Price Alerts, package routes and customer account destinations had incomplete catalogue coverage. | The earlier catalogue contained inactive or missing paths. The current registry records implemented routes and explicit exclusions. |
| Existing optional journey writes did not consistently check the environment of their exact source. | The gap predated Phase 1. New client writes verify the owned, same-environment search and the eligible Visitor. |
| An older tab could send a pending event using the cookies of a replacement account, and an older grant could reuse a withdrawn credential. | The browser confirms the current Visitor and verified account together. Each optional request supplies an in-memory equality proof. The server verifies the match before touching the Visitor and independently validates consent and attribution. A withdrawn credential cannot create a fresh grant. Browser tabs running an older bundle refresh before they resume optional delivery. |
| A share or save observation could beat the search's deferred completion and lose the journey link. | This race predated Phase 1. An optional share can be visible on its own while the same occurrence retries. A verified late link enriches the existing row. Confirmed saves use the existing mutation audit and never add a second save record. |
| A canonical package operation created a parent history row only for crawlers. | This predated Phase 1. The canonical route now records one executed `PACKAGE` request for a verified account or eligible Visitor. It reuses the search history writer and links an optional journey through the same consent and ownership safeguards. |
| The guided web package flow did not have a parent operation in Activity. | The pre-existing web flow enters a guided route and loads product inventory later. Validated explicit submissions send `Package search submitted` when analytics is eligible. Standalone component records retain their own products, and the submission carries no completed-search or provider outcome. |

## Event authority, retention and display

| Event family | Purpose and identity | Data and storage | Visibility and exclusions |
| --- | --- | --- | --- |
| Customer destinations and sections | Record committed approved destination visits under server-confirmed analytics consent. Registered events require an exclusive link. Guests retain guest-at-occurrence provenance. | `AnalyticsEvent` `PAGE_VIEW`, deployment, occurrence UUID, safe page key, previous observed key when available, reported platform and separately verified search references. | Existing Users Directory permissions and current optional visibility policy. The catalogue excludes private credential and recovery surfaces, unsanitized route values, prefetches and automatic background work. |
| Results and decisions | Observe eligible results, details, explicit selection, supported changes, sorting and filtering. Require a matching source search, Visitor and deployment. | Existing `JourneyEvent` records and exact `SearchHistory` links. Only approved field or option identifiers and bounded observed result attributes qualify. | Eligible Activity History and Journey History. UI-observed prices and provider labels describe the displayed choice. |
| Share and save observations | Record the initiating consented context and the confirmed local or system outcome. Account mutation source remains authoritative. | Existing optional Analytics and Journey records. Copy and share-sheet actions retain their specific outcomes. | Existing history guards. Recipient identity and delivery success are outside the evidence. |
| Guided Package search submission | Observe the validated explicit package form submission, including a changed search submitted from the guided editor. Require confirmed browser analytics and the activity owner's eligible Visitor. | `AnalyticsEvent` `SEARCH`, exact name `package_search_submitted`, closed package mode, reporting environment, scope and occurrence ID. | Activity's Customer and Package filters. Retains the established optional visibility policy. Stores no criteria, source URL, provider data or standalone search count. |
| Canonical Package search | Account for one actual execution using the existing search purpose for verified accounts, eligible Visitors and existing crawler accounting. | `SearchHistory` `PACKAGE`, public request UUID, terminal status, duration, closed mode/scope and component result count. An eligible Visitor can receive an exact `SEARCH_COMPLETED` journey event. | The existing Search and Activity permission model. Counts represent returned component results. An unidentified guest creates no new Package history. No component fan-out rows, bundle claims or raw search fields are added by the parent writer. |
| Security audit projection | Read allowlisted successful administrative audit evidence for the authenticated actor recorded by the existing writer. | Existing `AdminAuditLog` with explicit deployment evidence. The UI projects a fixed safe action label. | Requires the Audit Logs viewer permission. The target of the administrative action retains no actor authority. Older untagged audit history remains accessible through the audit source under its current rules. |
| Admin behavioral navigation | Dormant event definition and validation for eligible Admin destinations and sections. Permission requires a separate approved employee monitoring policy. | No runtime collection, storage, client bridge or live toggle is wired. See the Admin contract for the proposed bounded payload. | Activation requires written purpose, scope, transparency, viewer permission, retention and deletion approval. Customer consent has no role in enabling this. [Admin behavioral contract](admin-behavioral-activity.md) |

The implementation uses the existing data and deletion architecture. Optional visibility follows current Visitor consent and attribution. Existing operational search accounting, confirmed account mutations, legitimate Admin audit, online presence and Device & Access remain governed by their source rules. There is no schema migration, historical rewrite or new retention duration.

The browser confirmation proof derives from the existing HttpOnly Visitor credential and actor. The proof is an equality check against the independently verified request and is held only in memory. It conveys no account or Visitor authority by itself and is excluded from event storage. Consent withdrawal invalidates pending delivery. Previously stored optional rows follow the established current-consent visibility policy.

## Verification evidence

The browser suite ran Chromium against a Next.js application and migrated disposable PostgreSQL 16. It used synthetic accounts and blocked external browser traffic. The registered case exercised the actual risk path of an administrator using the customer interface. It verified the unsaved consent suggestion, server confirmation, account merge, the exact persisted actor, failed delivery and retry with one occurrence, concurrent replay, the actual Admin Pages Visited UI, the Package submission in All activity, optional share enrichment and withdrawal. The mobile web case verified the route remained silent before explicit consent and attributed an eligible page to the guest, with mobile web reported as the platform.

The disposable search/journey suite passed 27 cases including canonical `PACKAGE` deduplication, guest withdrawal, exclusive account claims, exact deployment matching and account retirement. The final Admin journey suite passed 19 cases including scoped reads, consent, actor-safe audit projection and exact linked Package page evidence. PostgreSQL exposed a column mismatch in Journey Details when the initial candidate added edit fields. The corrected query and added regression verify the existing detail shape, allowlisted hotel edit fields and exclusion of foreign owner, product and environment rows. The focused web suite passed 285 tests.

The full native suite passed 2,571 tests and the native type check passed. Synthetic iOS and Android requests exercised actual session grant and withdrawal handlers, no-token rejection, same-template detail instances, concurrent replay, exact canonical Package linkage and platform-specific share outcomes against the running application and disposable PostgreSQL. The transport tests use platform declarations. Installed-device acceptance is pending. The local travel parity suite passed 405 tests and the disposable Preview ledger suite passed 259. The existing Preview classifier now includes the three shared runtime dependencies used by native search edit tracking.

The 10,000-row PostgreSQL benchmark used identical seeded data for both arms, with 41 verified accounts and Visitors, refreshed statistics, one warmup and 16 measurements per operation. The runtime comparison used the original deployed `72bc7ffe` and rebased application revision `b9f757a09`. 2. After the separate merge and staging delivery approval, use the existing Render and Preview release workflows. Confirm the web deploy reports `live` for the approved SHA. 3. Verify the web endpoints and Activity History on dedicated staging test identities and supported suppliers or fixtures, then run the consolidated acceptance programme. Preserve the separate authorization boundary for any employee-monitoring acceptance.
4. ## Consolidated acceptance preparation

These checks use the controls confirmed in the isolated running interface. Run them together only after the candidate reaches an approved acceptance environment, with a registered test account, a separate Administrator and clean browser profiles. Use fixtures or authorized searches and stop before completing supplier operations.

1. Open the customer Homepage in a clean desktop profile. Select **Cookie preferences**, inspect **Analytics cookies**, then select **Close cookie preferences** without saving. In Admin, open **Users & Bots → Users Directory**, then **View Activity** for the test identity. The unsaved selection should yield no optional page activity.
2. On the customer Homepage, select **Accept all**. Open the visible **Hotels** link. In Admin go to **Users & Bots → Users Directory**, open **View Activity** for that identity, and select **View all pages visited**. Confirm **Pages Visited History** has **Homepage** and **Hotels**. The activity belongs to the same registered account when the Administrator performs it on the customer site. Repeat on mobile web as a signed-out consented guest and verify guest attribution and reported platform.
3. From **View Activity**, select **View all activity**, set **Activity interface** to **Customer** and select **Apply filters**. Check the eligible customer rows for the tested actor. Select **Admin** with an authorized Audit Logs viewer and compare an existing allowlisted operation they actually performed with the actor audit source. Opening another person's Activity creates no customer event for that person. Keep new Admin behavioral collection disabled throughout.
4. Return to customer **Cookie preferences**, switch **Analytics cookies** off and select **Save preferences**. Navigate to **FAQs** and refresh the corresponding **Pages Visited History**. The withdrawn Visitor's optional pages should be hidden. In the same session, verify an eligible essential action still appears through the existing search or account source. Retest with another tab open and when switching between two test accounts.

The complete acceptance session also needs controlled Flight, Hotel, Car and Package results with offer details, edits, filters, sort, sharing, saves, alerts and provider handoffs. It should reconcile All activity, Pages Visited, Journey History and Journey Details against exact fixture events. Confirm the installed iOS and Android builds, their controls and the staged test inventory before issuing device steps. Their acceptance also covers guest refusal and withdrawal, account switching, same-template details, returning to a prior screen and the distinction between requesting a share sheet and verified OS completion. In a separate authorized technical run, assert exact event ownership, rejected actor and deployment mismatches, stable UUID retries and database rows. The tests that inject errors, read browser requests or query PostgreSQL require engineering access.
