# Admin behavioral activity

Admin page and section activity is disabled pending employee monitoring approval. The coverage registry lists 55 canonical Admin page templates, 10 redirect-only aliases, 60 page-specific section entries and 7 identifiers for common shell panels and sections. The same definitions apply to Admin desktop and mobile web. No browser observer, API endpoint, database writer or history reader is mounted for these records. The existing security audit writers retain their own authorization, data and lifecycle.

| Definition | Purpose and category | Required authority and identity | Data and destination | Visibility and lifecycle |
| --- | --- | --- | --- | --- |
| Admin page visit | Observe an authorized, committed destination in an approved Admin workspace. `page_visit` | Verified Admin access, authenticated actor account, matching initiating session and explicit approval of the destination | Closed page template, actor account ID, Admin interface, web platform, environment and occurrence UUID. No active storage destination. | A viewer permission and reviewed retention and deletion policy are required before activation. |
| Admin section visit | Observe deliberate opening or selection of a reviewed Admin section, tab or panel. `section_visit` | Same authority as a page visit, with explicit approval of the section key | The same fields as a page visit, with a closed section identifier appended to the template. No active storage destination. | Same requirements as a page visit. |

The page templates come from `routes.admin.deferred` in `config/activity-tracking/definitions.json`. Those declarations account for main navigation, workspace and Settings sidebars, breadcrumbs, linked cards, direct detail pages and conditional destinations such as Team Access. Redirect aliases are listed separately with reasons. The `adminBehavioralSections` entries describe committed subsection choices such as the Providers Referral Attribution view, activity and directory tabs, notification and workspace search panels, trip monitoring sections, and selected details in Support, Providers, Bots and Audit Logs. A definition is a candidate for explicit policy review. It does not establish that a control appeared, was enabled or was used at runtime.

The recorder accepts observations from a trusted adapter after confirmation that a destination rendered or a section was deliberately activated. The default has no approved scope and makes no writer call. A proposed integration must obtain the actor, access and environment from verified server context. Approval must cover the purpose, employee notice, destination, viewer permission, and retention and deletion handling. Customer cookie consent does not grant any of these permissions. Changes or withdrawal of a policy must invalidate pending collection. Recheck approval at persistence and before any future history read.

The current contract takes an occurrence UUID from the committed observation. It normalizes retries to the same ID and delegates atomic append or replay acknowledgement to the storage adapter. A matching initiating session is required. Two committed visits to different records under one route template use separate occurrence IDs. The stored shape contains only the template, defined section and actor. It contains no viewed-account identifier, route parameter, raw URL, query, arbitrary form value, search term, support message, audit payload, credential, raw device data or request evidence. Previous sections require verified same-context provenance from a future adapter. New behavior records may not be sent through the Customer page or journey endpoints or written as security audit entries.

Prefetch, polling, automatic refreshes, redirects, failed navigation, generic menus and form editing are outside the definitions. For mixed automatic and deliberate controls such as automatically expanded trip delivery alerts, only the confirmed deliberate opening is eligible. Security-sensitive confirmations and mutation outcomes remain under their owning operation and existing audit authority. A UI click supplies no action outcome.

Synthetic tests cover catalogue safety, missing or incomplete approval, destination scope, account switching, actor ownership, and duplicate and distinct occurrences using an in-memory sink. Live collection, database performance and history display remain disabled pending review of the server integration and storage lifecycle.

## Existing security audit projection

The Users Directory reuses the existing `AdminAuditLog` as a source for successful account role, suspension, reactivation, deletion and team access mutations already covered by administrative security auditing. Those existing writers include the current deployment in new eligible audit entries. This categorizes the existing `security_audit` record for incident review and access accountability. The source authenticated Admin account ID determines the actor, even when an affected account has the same email or appears in an action's URL.

Activity and All Activity apply the same active, verified and allowlisted Admin viewer check as Audit Logs. They project the closed action label, recorded timestamp, Admin interface, Administrator at occurrence, and confirmed successful outcome. This projection excludes subject IDs and emails, IP and user-agent values, reasons, raw audit metadata, untagged historical rows and actions from another deployment. Rows continue under the existing Audit Logs lifecycle and retention and consume no additional storage. Legacy rows retain their existing Audit Logs availability. Rejected and failed outcomes require source evidence and do not receive a synthetic record.
