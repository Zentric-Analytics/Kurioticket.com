# Bot security and monitoring

The Next.js proxy alongside `src/app` is the active ingress. The former root middleware performed region selection and account two-factor enforcement. It took precedence over the staging document-cache proxy in the previous build. The consolidated proxy applies bot policy before those behaviors and checks static resources, API requests, and legacy Deals redirects. Next's own early URL normalization and traffic served or blocked upstream remain outside application observation.

The crawler catalog defines the seven search engines, plus recognized AI, social, Google service, SEO, and archive crawlers. Only a verified search engine can submit a canonical search. All recognized crawlers, including declared search engines, may crawl approved public pages. Verification determines eligibility for limited search. Unrecognized automation is blocked. An upstream denial remains recorded as a denied event. Missing cookies, consent, platform headers or account identity do not constitute automation evidence. Browser-equivalent automation without a trustworthy signal cannot be reliably distinguished from a human.

## Identity and ingress configuration

- Googlebot uses forward-confirmed reverse DNS under the Google common-crawler hostnames. Bingbot uses forward-confirmed reverse DNS under `search.msn.com`, with the [published Bingbot IP list](https://www.bing.com/toolbox/bingbot.json) as a fallback for an authenticated ingress IP. Applebot uses `applebot.apple.com`. YandexBot uses the documented Yandex reverse DNS domains. Baiduspider and Yahoo Slurp are accepted only in their crawler-specific DNS namespaces (`crawl.baidu.com`, `crawl.baidu.jp`, `crawl.yahoo.net`). DNS lookup failure or mismatched forward records deny search access. Baidu and Yahoo declarations with other host patterns receive crawl-only access unless an authoritative verification method is added.
- DuckDuckBot uses exclusive host addresses from DuckDuckGo's official HTTPS list. Unavailable or unrecognized data cannot establish identity. Broad prefixes are rejected. DNS lookups are time-bounded and use short negative caching and bounded concurrency.
- GPTBot, OAI-SearchBot, ChatGPT-User, PerplexityBot, and Perplexity-User use their respective operator-published address lists. Verification retains crawl-only access. Google's common and special crawler ranges cover multiple products, so GoogleOther, Google-InspectionTool and Mediapartners-Google stay self-declared unless product-specific evidence is available. The catalogue also keeps Meta-WebIndexer, Meta-ExternalAgent, Meta-ExternalFetcher, FacebookExternalHit, ClaudeBot, Claude-User, Twitterbot, LinkedInBot, Bytespider, AhrefsBot, SemrushBot, ia_archiver, MJ12bot and AASA-Bot self-declared in the absence of a configured, product-specific check. General operator ownership and multi-product network lists are insufficient to authenticate those declarations.
- Verification uses the address from Cloudflare only when the request carries an authenticated edge assertion. A request header naming a country, crawler, score, or connecting address has no independent authority. Set a separate high-entropy `BOT_EDGE_SECRET` in each environment and use a Cloudflare Worker or equivalent trusted edge to remove inbound `X-Kurioticket-Edge-Auth` and `X-Kurioticket-Edge-Bot`, inject the edge secret, and forward the Cloudflare-observed address. Keep the assertion internal to the edge-to-origin request. If the account exposes a high-confidence automation signal, the edge can send `X-Kurioticket-Edge-Bot: automated`. Configure edge rules to preserve legitimate native traffic, platform jobs and search engine verification. A verified-bot category alone does not authorize a search.
- After confirming both public hostnames, mobile clients and scheduled calls traverse the asserting edge, enable `BOT_REQUIRE_EDGE=true` on each Render web service to reject direct-origin traffic. The existing GET/HEAD `/api/health` remains available to Render health checks. In unconfigured environments, backend policy still blocks unrecognized automation and denies search to all unverified claims.
- Ensure Cloudflare bypasses response caching for protected, search, and bot traffic if those requests must reach application monitoring. Use WAF filtering and rate limits supported by the zone to reduce traffic before it reaches Render. Do not use login status, generic User-Agent matching or analytics consent as an edge challenge condition.
- If the Cloudflare plan exposes blocked-request logs, forward explicit bot-related **block** or **rate-limit** outcomes from the log pipeline to `POST /api/internal/bot-security`, using `Authorization: Bearer <BOT_OPERATIONS_SECRET>`. Submit one bounded JSON event with `ray` (lowercase hex without colo suffix), UTC `timestamp`, `path` (omit query), `method`, `status` (403 or 429), and optional `userAgent`, `ip`, `country`. The intake deduplicates by environment and ray. Keep the writer credential separate from the edge secret. Importer, WAF and dashboard configuration require zone access and vary by plan. The repository identifies Cloudflare-backed Render ingress and contains no zone settings or export entitlement. No live zone or service changes are part of this PR.

Official references: [Google](https://developers.google.com/search/docs/crawling-indexing/verifying-googlebot), [Bing](https://www.bing.com/webmasters/help/how-to-verify-bingbot-3905dc26), [Apple](https://support.apple.com/en-us/119829), [DuckDuckGo](https://duckduckgo.com/duckduckgo-help-pages/results/duckduckbot), [Yandex](https://yandex.com/support/webmaster/en/robot-workings/check-yandex-robots), [Cloudflare request headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

## Search boundary and accounting

Only the canonical POST endpoints for Flights, Hotels, Cars and Packages admit a verified search engine. Nearby fares, progressive hotels, flight inventory, and provider-specific alternatives are outside the bot search surface. The package orchestrator's in-process fan-out shares its parent execution. Website and native provider paths continue to use their existing accounting and controls.

PostgreSQL serializes a verified identity's reservation in its configured environment. The timestamp comes from the database after taking the lock. A request must pass product validation before reservation. The store enforces five dispatches per UTC calendar day and a rolling 30-minute cooldown, including across midnight. The provider call uses the activity UUID as its correlation ID. A supplied retry ID is hashed and scoped to the bot identity. A duplicate dispatch ID returns 409, and quota denial returns 429 with `Retry-After`. An aborted request before the reservation does not consume quota. Once dispatch is committed immediately before invoking the provider orchestration, errors and empty results retain the slot. A crash between the commit and invocation is indeterminate and conservatively retains the slot.

Existing bot search rows continue to use `BOT` and crawler attribution, and no customer session is written for them. Activity and historical/provider records are correlated by the generated request UUID. The migration creates two new tables only. It does not update historical search and reconciliation records.

## Reporting and retention

Active, verified, configured administrators can read `GET /api/admin/bot-activity`. The paginated registry view exposes lifetime totals and current quota. The activity view supports UTC `from` (inclusive), `to` (exclusive), identity, group, verification, decision and type. Search entries include related history and available provider log references. Without date parameters, reports return all retained events. Registry date filters select first-seen identities. Report responses are private and uncached.

Events separate protected paths, public crawl observations, resources, API attempts, and search dispatch. Observations use known route templates and catalog product tokens. Raw query strings, credentials, arbitrary headers and bodies are excluded. Shared unknown labels are observation cohorts, and multiple observations do not imply one physical client. Proxy-allowed reads are ingress observations. The proxy cannot report the downstream page response or indexing outcome. Application denials, search responses, and imported edge blocks have observable status codes.

Keep detailed activity and idempotency hashes for 90 days. Schedule authenticated `DELETE /api/internal/bot-security` daily through the edge in each environment, using the operations secret. Repeat while a batch deletes 10,000 rows. Registry lifetime counters remain available after event pruning. Deploy the additive migration before serving the new code. To roll back, disable the optional edge requirement and revert the application release. Keep the additive tables and data for investigation and a future forward rollout.

## Original network evidence handoff (staging-first rollout)

The shared edge assertion is required for trusted bot evidence in **all** categories, including blocked/unknown requests. Staging database evidence can be missing even when Render access logs contain client addresses. Do not substitute raw client-supplied forwarding headers or authorize based on a declared name. The optional version-1 envelope carries the original edge-observed IP, country, Ray ID, ASN and ASN organization in dedicated headers before an upstream proxy rewrites Cloudflare headers. Existing authenticated legacy assertions remain supported. Missing/invalid values are null; ASN/organization is network attribution, not proof of bot ownership. The network fields are retained only with bot activity for the existing 90-day retention period. No historical data is inferred or reclassified.

Use `tools/cloudflare/bot-edge.mjs` on an existing proxied DNS hostname via a Worker **Route**, not a Worker Custom Domain. Review existing Workers, routes, caching and WAF first. Deploy the additive Prisma migration and application in staging, then set a distinct high-entropy `BOT_EDGE_SECRET` in the staging Render web service and matching Cloudflare Worker secret binding. Set the Worker's `BOT_EDGE_HOST` to `staging.kurioticket.com`, disable public workers.dev/preview URLs, and attach the route `staging.kurioticket.com/*`. The Worker strips all incoming internal headers, copies Cloudflare's original metadata, forwards the request to the existing origin using manual redirects, and never logs the secret. Do not attach to a hostname that is not verified or replace an existing Worker blindly. Do not enable BOT_REQUIRE_EDGE until public clients, Android/iOS, authentication, background jobs and health checks have passed staging verification. Roll back by removing the new route and restoring the prior edge configuration; keep additive columns. Production requires its own separately approved rollout and secret.

The Worker strips any client-supplied automation assertion, then restores it only from Cloudflare's trusted `request.cf.botManagement` metadata when `score === 1` and `verifiedBot === false`. This uses Cloudflare's definite-automation classification rather than likely-bot scores (2–29). Missing or malformed metadata never becomes a trusted automation signal, and Cloudflare-verified bots are not marked suspicious by this classifier. That verification flag does not grant Kurioticket access: existing catalog, DNS, route and quota checks still apply. See [Cloudflare Bot Management variables](https://developers.cloudflare.com/bots/reference/bot-management-variables/) and [Cloudflare's definite-bot guidance](https://developers.cloudflare.com/bots/get-started/bot-management/). Bot Management availability and classification of legitimate API, mobile and scheduled clients must be confirmed in the target zone before activation. Browser-equivalent automation can remain undetected when trusted metadata is missing or inconclusive. WAF-blocked requests never reaching the Worker require the authenticated edge-event intake described above (now also accepts optional networkAsn and networkOrganization). Neither the Worker nor the intake changes search quotas or crawler approval rules. Admin Bot Details exposes recorded network evidence per retained request and the latest 20 observations for every category.

Acceptance: verify valid assertions reach Render; spoofed or direct unasserted metadata does not confer trust; ordinary humans/native clients are unaffected; genuine Googlebot/Bingbot are verified through existing DNS rules; check the remaining catalog categories and unapproved bot attempts; verify network fields and Ray correlation in staging. Compare only uniquely correlated retained events to historical logs in a separate reviewed reconciliation; do not rewrite old access decisions or manufacture missing evidence. Live verification is required before declaring the incident resolved.

### Trace an observed request on Render

Open the individual event in Bot Management, copy its Render request ID and search for that exact requestID in the same service's HTTP request logs. Check its client IP alongside the authenticated ingress evidence on the event. The ID is for correlation only. Older events and imported upstream denials can lack a Render request ID. See [Render request tracing](https://render.com/docs/logging#tracing-with-requestid-and-rndr-id).
